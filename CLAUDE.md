## Architecture

This project ships two separate products from one codebase:

### 1. Web Dashboard (Express + React SPA)
- **Server** (`server/`): Express 5 app with REST API. Runs on port 5001 by default (`PORT` env var). In dev mode, Vite middleware is injected after API routes.
- **Client** (`client/src/`): React 18 SPA using wouter for routing, TanStack Query for data fetching, Tailwind + shadcn/ui components.
- **Database**: SQLite via `better-sqlite3` + Drizzle ORM. Path defaults to `./sqlite.db`, override with `DATABASE_PATH` env var.
- **Shared schema** (`shared/schema.ts`): Single source of truth for DB tables, Drizzle types, and Zod validation schemas — used by both server and client.

### 2. Chrome Extension (MV3)
- **Content script** (`client/src/extension/content.ts`): Injected into every page. Handles text selection, DOM wrapping with `<mark class="wh-ext-mark">`, toolbar/dialog UI injection, and highlight restoration on page load.
- **Background service worker** (`client/src/extension/background.ts`): Manages `chrome.storage.local` as the extension's offline data store. Routes messages from content script, handles context menus, and orchestrates sync to/from the web server.
- **Extension UI pages** (`client/src/extension/popup/`, `dashboard/`, `options/`): React apps built as separate HTML entry points.

### Dual queryClient pattern
The extension UI pages reuse the same React components as the web dashboard, but swap the data layer at build time:
- Web app uses `client/src/lib/queryClient.ts` → HTTP `fetch()` calls to `/api/*`
- Extension uses `client/src/lib/chrome-query-client.ts` → `chrome.storage.local` reads/writes

`vite.extension.config.ts` aliases `@/lib/queryClient` to the Chrome version. `vite.extension-scripts.config.ts` builds `content.ts` and `background.ts` as plain ES library files (no React).

### Path aliases (in all Vite configs)
- `@` → `client/src/`
- `@shared` → `shared/`
- `@assets` → `attached_assets/`

## Key Data Flow

**Creating a highlight (extension)**:
1. `content.ts` detects text selection → shows toolbar
2. User clicks Highlight → `wrapRangeWithMarks()` wraps DOM text nodes in `<mark>` elements
3. Sends `SAVE_HIGHLIGHT` message to `background.ts`
4. `background.ts` writes to `chrome.storage.local`
5. On next page visit, `content.ts` calls `restoreHighlights()`, which re-applies marks using stored xpath + textOffset

**Syncing extension → server**:
Extension popup triggers `SYNC_TO_SERVER` → `background.ts` POSTs to `/api/pages` then `/api/highlights` and `/api/comments`, marking items as `synced: true`.

## Server Storage Pattern

`server/storage.ts` exports a `DatabaseStorage` class implementing `IStorage` interface. All DB operations go through this class. `seedDefaults()` is called on startup to populate initial highlight styles and sample data when the DB is empty.

## Extension Build Output (`dist/extension/`)
```
manifest.json          (generated by script/build-extension.ts)
icons/                 (16, 48, 128px PNGs)
src/content.js         (content script)
src/background.js      (service worker)
src/content.css        (highlight styles)
popup/index.html       (popup UI)
dashboard/index.html   (full dashboard)
options/index.html     (settings page)
assets/                (JS/CSS chunks)
```

Load the `dist/extension/` folder as an unpacked extension in `chrome://extensions` with Developer mode enabled.
